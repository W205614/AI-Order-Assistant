# 校园多店点餐实现说明

本次扩展保留单 Java、单 Python Agent、共享 MySQL 的部署方式，每个商户仍对应一家店。支付、退款和优惠成本均为模拟台账，没有真实资金、地图定位或骑手工资结算。

## 使用入口

- `/campus/`：顾客跨校区选店、购物车、优惠、统一结算、预约自提、退款、收藏和反馈。
- `/admin/`：原菜单及库存功能保留；新增校园订单处理、规格套餐、服务校区、券活动、预约和售后。
- `/platform/`：新增校区、平台券、骑手开通及校区授权、指派改派、异常、争议售后和经营台账。
- `/rider/`：授权校区任务池、抢单、取餐、送达码核验及异常报告。
- `/chat/`：原单店对话与本店临时过敏约束确认仍可使用。

平台先创建校区和商户，商家配置店铺所在地及目的校区配送规则。跨校区服务默认关闭，必须明确开放。自提只允许店铺所在地，单份结算不可混用配送、自提或多个收货地址。

## 商品与库存

原菜品自动映射默认 SKU。默认 SKU 通过库存适配器共用原 `dish.stock`，不复制一份可独立修改的计数器，因此原单店下单和新跨店下单竞争同一库存。新增规格在 SKU 中维护库存；更新规格不能覆盖库存，使用版本及幂等库存调整接口。

固定套餐绑定同店 SKU 及数量，确认时合并套餐和单品的组件需求后扣减。套餐按份售卖、按份退款，不拆退其中组件。包装费只取套餐自身价格，不再叠加组件包装费。加料是独立商品规格。过敏校验读取所有组件，购物车保留当时的过敏约束，不能通过等待临时约束过期绕过。

## 结算与报价

服务端购物车按顾客、店铺分组持久化。报价有效五分钟，不占库存和优惠券。报价包括每店商品、包装、配送、两类优惠、实付及不可提交原因。

顾客选择剔除不可用店铺后必须重新报价、核对并点击确认。确认采用一笔数据库事务创建结算和所有选中的店铺订单，同时预留 SKU 库存、预约容量及优惠券；失败整体回滚。事务内不调用模型或外部支付。地址、商品、优惠、配送规则或购物车版本变化要求重新报价。JSON 快照按数值语义比较，保留价格变化拦截，不因数据库小数表示变化误报。

确认幂等键绑定用户、报价及版本；同键不同内容拒绝，同报价也不能创建第二份结算。支付截止十分钟，每十五秒扫描超时补偿。一次模拟支付覆盖全部子订单，支付前取消任一子订单关闭整份结算。支付后各店独立履约和退款。新订单禁止通过旧单店接口单独支付、取消或推进状态。

顾客历史结算支持 `GET /checkouts?page=1&pageSize=20`，页面可加载更多并在刷新时保留已加载页数；不传参数保留原每页 100 条响应数组契约。商家校园队列显示商品、备注和预约明细，旧订单队列只处理旧版订单。

库存操作统一先按父菜品标识、再按 SKU 标识升序加锁；券先锁活动再锁券，预约容量在其后处理。订单单位按不可变主键当前读和精确更新，避免区间锁及等待后的旧快照影响库存。事件在提交前统一持久化，最后获取共享游标锁，仍与业务同事务提交或回滚。

## 优惠与退款规则

每人每活动最多领取一张券；发行量、领取时间和使用时间由后端控制。每店一张店铺满减券，每份结算一张平台券，两类可叠加。起送门槛按优惠前商品金额判断；店铺券先抵扣，平台券门槛按店铺优惠后的商品金额合计计算。包装费与配送费不参与优惠。

平台优惠按各店剩余商品金额分摊，优惠进一步分摊到每份商品。使用两位小数及最大余数法分配尾差，以稳定标识顺序打破平局，保证总额一致。历史订单保存价格、组件、数量及优惠快照，退款不重新套用满减门槛。

制作前按数量申请立即模拟退款，回补对应组件库存；最后一份商品取消时同时退本店配送费、释放预约容量。整店取消退剩余实付，已退商品不重复回补。制作后申请占用可退份数，由本店审核；平台处理被驳回后的申诉。批准后退原商品实付及包装费，不退配送费、不回补食品库存。待审核、已退份数共同限制剩余可退量。

仅在本店全部商品制作前取消时返店铺券；整份结算所有商品均制作前取消才返平台券。返还不延长有效期，部分退款及制作后售后不返券。店铺券由店铺承担、平台券由平台承担，报表区分支付、退款、净收款、完成净额及保留商品的优惠成本。

## 履约与预约

商家接单、开始制作、备餐完成。配送单备餐完成后生成唯一任务；授权目的校区的骑手可抢单，接单前不展示收货人、电话及详细地址。一个任务只能有一位有效骑手，平台可按版本指派或改派。取餐后不能自行放回池中，异常由平台指派接续骑手，保留已取餐事实及操作原因。

取餐/送达码只允许订单顾客查询，不进入事件、审计或模型工具。核验错误累计十次锁定，由平台核实身份后解锁。自提核验完成不生成骑手任务。

商家开放未来七天内、营业时间内的预约时段，设置截止时间、容量及备餐提前量；时段最长四小时。确认占位，支付超时和制作前整店取消释放。商家可以提前接单，但到备餐时间才允许开始制作；后端队列按可备餐优先展示。预计送达与自提时间为区间，不承诺精确到达。

平台异常列表包含配送异常、待接任务积压、长期未接单、预约到期未制作、长期未取餐。系统不自动判定送达，也不因异常自动退款。

校园页菜单上方可按当前店铺确认或清除花生、鸡蛋、麸质临时约束，无需跳转单店页。聊天标记待确认后，涉及的店铺需分别确认。有未保存选择或正在保存时，页面要求先完成确认再发起加购、复购、购物车对话或报价；刷新菜单及保存失败保留选择，进行中的保存按店串行。清除仅作用于临时上下文，长期偏好和已有购物车的安全快照继续有效。

页面列出各店未保存选择及来源校区，可返回对应店铺确认，也可只放弃本页未保存选择。切校区、切店时，过期导航响应不能覆盖当前选择。聊天失败后尝试重新读取菜单与安全上下文，避免服务端已标记待确认而页面仍显示旧状态；同步失败时提示刷新。手动报价的过期响应也不能清除后续已通过校验的助手报价。

## AI 与权限

校园 Agent 使用独立 `/campus-chat` 协议和固定的平台额度范围 `0`，保留原 `/chat` 协议。Java 固定顾客、目的校区、地址和履约方式；模型无法通过工具参数更改这些上下文。工具只开放安全菜单搜索、有限预算组合、本人券/购物车/结算查询、购物车准备和报价。

组合搜索每类关键词取有限候选，最多三个关键词，最多返回三个经过实际报价验证的组合。它是可行方案搜索，不保证全局最优。未配置模型或 Agent 停止时，菜单、购物车、报价、确认和模拟支付仍由 Java 提供。

“我已在页面确认过敏约束，继续推荐”等窄范围确认引用，仅能复用该顾客、该店有效且已确认的安全上下文，不重写或续期。首次声明、待确认、过期或新增约束不会被此句绕过。模型可见工具数据将顾客约束命名为 `appliedCustomerAllergens`，避免将购物车的安全约束快照误读为菜品含有的成分；原始 Java DTO、报价和确认契约保持不变。

近期对话按顾客、校区、地址、履约方式隔离，最多保留最近三轮文本，保存时设置十五分钟有效期，并受文本大小和存储容量限制，不接受浏览器自带历史作为可信上下文。购物车写工具只接受完整的明确写指令及支持的限定子句；提问、引用、假设、否定和不支持的混合表达会在 Java 调用前被拒绝，并提示用户重述。该门槛不校验模型参数是否与用户想选的商品、数量完全一致，仍需本人核对购物车。写入仍经 Java 的服务校区、本人地址、商品安全与版本校验。助手返回的结构化报价只有与页面当前条件及购物车版本一致才可展示确认按钮；自然语言中的金额不会用来创建订单。

聚合入口按顾客归属授权，商家按商户授权，骑手按任务与服务校区授权。平台审核、改派与配置留存审计。顾客和骑手事件通过持久游标补读，业务列表是最终状态依据。

## 迁移与验收

V6 为增量迁移：旧商户归属默认校区并拥有零费用本校区配送规则，原文字配送区域、订单和支付记录保留。旧订单版本为 1，新结算订单为 2，两个处理路径明确区分。升级前备份并保留旧镜像；数据库升级后的回滚必须使用对应备份恢复至独立库验证，不能直接让旧应用读新结构。

可复现检查：

```powershell
mvn -B -ntp test -f java-gateway/pom.xml
node scripts/check-static-js.mjs
Push-Location agent-service
python -m unittest discover -s tests -v
Pop-Location
node scripts/test-campus-browser.cjs --base-url http://127.0.0.1:19090
python scripts/check-load-invariants.py --project ai-order-campus
```

Python 检查需使用项目锁定依赖环境；也可在隔离 Agent 容器中只读挂载 `agent-service/tests` 执行。浏览器脚本只允许本机隔离端口，准备两个校区、三个店铺、两个骑手并执行跨店双券、剔除不可用店、数量退款、配送、自提和预约流程。真实模型端到端结果与固定工具测试分别记录，不能互相代替。

真实提供商验收需要显式启用，会产生模型费用。默认 `deploy/compose/isolated.yml` 清空模型密钥，CI 不运行付费模型测试。手动验收时，通过当前进程的环境或不入库的私有 env 文件提供 `CAMPUS_EVAL_LLM_API_KEY`、`CAMPUS_EVAL_LLM_BASE_URL`、`CAMPUS_EVAL_LLM_MODEL`，在根 Compose 与 isolated 覆盖文件后叠加 `deploy/compose/model-eval.yml`，再运行：

```powershell
python scripts/test-campus-live-model.py --base-url http://127.0.0.1:19090 --report .local/campus-live-model.json
node scripts/test-ui-quality.cjs --base-url http://127.0.0.1:19090 --report .local/ui-quality/results.json
```

真实模型脚本建立独立测试账号、校区、店铺与券，检查提供商 usage、实际工具调用、持久购物车及 Java 报价，不确认或支付订单。私有 fixture 包含测试账号密码，不能入库；报告不记录密钥、JWT、地址详情或取餐码。`--reuse-fixture` 只复用并清空该测试顾客的购物车；其他顾客数据不变。UI 检查可选择 `--fixture` 验证登录后角色页面；`--model-message` 额外调用真实模型，必须同时提供 fixture。Playwright 与浏览器路径参数沿用校园浏览器脚本。

UI fixture 的 `password` 默认供顾客及可选角色登录；店主、骑手另行开通且密码不同时，可分别设置私有 `ownerPassword`、`riderPassword`，不应修改产品账号来迁就测试夹具。

最新部署与模型复验见 [最终部署与真实模型验收](verification/2026-10-15/最终部署与真实模型验收.md)，首次扩展结果见 [校园平台验收](verification/2026-10-15/校园平台验收.md)。升级后恢复演练使用 `restore-db.ps1 -CampusSchema`，同时检查校园交易指纹；旧版本备份不传该参数。

运行层命名为 `runtime`。安全更新需要刷新系统包时，可用 `docker build --no-cache-filter runtime -t ai-order-assistant-gateway java-gateway`，复用 Java 构建缓存并重新执行运行层系统包更新；构建后重新扫描，不能把缓存镜像的旧扫描当成新版本结果。
