# 多商户 AI 点餐助手实现与验收

本次完成的是个人可维护的多商户演示第一版：平台开通商户、每商户一店、模拟支付、商家手动履约。核心隔离、交易、安全和恢复场景已验证；公网证书、真实资金、最大容量和长期稳定运行没有作为已完成成果。

## 版本与环境

- 改造前：`0bcfc41`；功能改造：`7ed9aad`；依赖锁定及故障演练：`fb6c980`；安全修复：`addeb1c`；提示与预算修正：`b81551f`；事务截止检查：`32f3489`；后端交易实现与草稿冷启动修复：`66b44ad`；浏览器体验与最终启动脚本：`3298924`。后续前端改动未改变后端交易实现，完整业务压测绑定 `66b44ad`。
- Java 21 / Spring Boot 4.0.8、Python 3.13、MySQL 8.4、Redis 7.4，Docker Desktop Linux 容器。
- 主机 AMD Ryzen 5 6600H，6 核 / 12 线程；Docker 可用 12 CPU、16,341,676,032 字节内存。测试时同机还有其他项目容器，环境没有完全独占。
- 隔离验收使用独立 Compose 项目和卷。原演示库升级前备份，未删除原项目卷；历史 28 笔订单、30 个明细、13 道菜、7 个用户和总库存 1270 迁移前后数量、订单及库存校验值一致，旧数据归属商户 1。之后的页面验收新增了测试账号和订单。[迁移证据](legacy-preservation.json)
- 本地运行入口：顾客 `http://localhost:9090/chat/`，商户 `http://localhost:9090/admin/`，平台 `http://localhost:9090/platform/`；监控 `http://localhost:19091/`。平台随机密码仅保存在本地 `.env`。

## 实现范围

| 模块 | 已实现行为 |
|---|---|
| 商户与人员 | 平台开通/停用；老板管理菜单、库存、营业设置和店员；店员处理本店订单；顾客先选商户 |
| 归属与权限 | 菜品、草稿、订单、流水、事件、临时约束与缓存按商户隔离；详情、修改、删除和工具回调重新核验归属 |
| 草稿与报价 | 每用户每商户一份活动草稿；修改/确认携带版本；价格或菜单版本变化返回 409 及最新报价，再次点击才能落单 |
| 交易 | 幂等键绑定用户、商户、草稿、版本和收货信息；锁定菜品后校验价格、过敏原、库存；按 ID 顺序加锁 |
| 模拟支付与补偿 | 确认预留库存；十分钟未支付关闭；支付后商家待处理；制作前取消释放一次库存并按需记录一次模拟退款 |
| 履约 | 店员/老板手动依次制作、配送、完成；禁止跳步与终态回退；顾客制作后不能取消 |
| 库存 | 增减接口、独立版本、幂等与流水；菜单编辑不能覆盖库存扣减 |
| 身份与输入 | Spring Security / Nimbus JWT，必需声明、算法、签发方、受众校验；HttpOnly Cookie / CSRF；退出、改密码和停用失效；登录/注册限流 |
| AI | 固定商户与用户；35 秒预算、8 总并发 / 每商户 2、输出与请求额度；取消只准备待点击操作；确定性 Router、FAQ 和模型降级 |
| 事件与审计 | 数据库持久审计和事件；SSE 心跳、连接限制、补读；提交后异步通知有界队列，失败不改变成功交易结果 |
| 性能与运维 | 商户复合索引、批量明细与解析、缓存元数据并覆盖最新库存/安全字段；依赖就绪检查、Prometheus、每日备份与独立恢复脚本 |

Java 保持单应用、JDBC 和兼容 `OrderService` 门面，拆分 Merchant、Menu、Draft、Inventory、Transaction、Query、Audit 等服务。前端拆成五个 ES 模块，包含顾客、商户和平台三类页面。Python 不直接访问业务数据库。保留现有偏好和过敏原拦截；FAQ、工具状态和提示词已同步模拟支付、退款与取消边界。

## 浏览器体验与最终容器

按真实页面流程修补了以下问题：支付与角色由英文枚举改为中文；加入购物车后显示件数与“去结算”；菜单限制滚动高度，保存草稿后定位结算、创建订单后定位订单；收货人、手机号、地址和区域有明确标签，信息不完整时不发送确认请求；价格冲突提示不会再被通用成功提示覆盖；空列表有说明、末页不能继续翻页；切换商户同步各店过敏约束；编辑菜品不再提交库存绝对值；登录信息和营业表单加载完成后才展示操作区；账号停用后返回登录，商户停用后停止新增点餐但保留历史订单查询。

移动端以 390×844 视口验证，无横向溢出；桌面与手机截图人工检查了文字、按钮、结算信息与中文订单状态。这是开发者检查与自动交互验证，未开展独立用户可用性研究，不能宣称用户满意度。完整浏览器脚本仅对隔离端口运行，创建的商户、账号和订单随临时数据库删除。

本项目现在仅保留 `ai-order-assistant` 下六个服务：gateway、agent、mysql、redis、backup、prometheus。验收/压测项目及三个失败的扫描容器已清理；原项目数据库卷和备份保留，其他项目容器未改动。启动脚本默认带上运维覆盖文件。[最终容器与监控](operations.json)

## 普通业务性能

这组结果使用后端业务版本 `66b44ad`，50 个此前没有草稿或订单的新账号、50 个 VU，持续 601 秒。Java/MySQL/Redis 使用独立 Compose 网络，压力流量直接请求 `http://gateway:9090`，未调用模型。之后的修改涉及页面、浏览器脚本、启动脚本与 CI，未修改后端交易实现。[完整指标](performance.json)

场景为菜单查询 → 创建草稿 → 确认及重试 → 模拟支付 → 取消及重试 → 订单列表，每次循环休眠一秒。单商户，13 道菜、161 个数据库用户，其中 50 个新账号参与本轮；初始 78,386 笔订单，结束 101,497 笔。测试开始库存合计 1,300,000；先前中断场景预留的四份库存在本轮自动超时释放，最终 1,300,004，每笔订单库存流水另行核验。该场景不能代替完成订单、多商户混合负载或售罄竞争；这些一致性问题由真实 MySQL 并发测试覆盖。

| 指标 | 实测 | 门槛 |
|---|---:|---:|
| 查询 P95 | 69.48ms | <500ms |
| 写接口 P95 | 200.22ms | <1000ms |
| 非预期错误率 | 0 | <1% |

一次以已有账号执行的十分钟场景通过后，补做新账号首次创建场景，在 `32f3489` 发现 26 项业务检查失败。MySQL 死锁日志指向活动草稿空范围更新与随后插入之间的间隙锁；修复为已存在草稿按主键更新，并保留用户行锁。新增八个新用户的真实 MySQL 并发用例通过后，`66b44ad` 完整重跑十分钟通过。失败没有被删去或作为成功计入。[首次失败与修复](performance-cold-regression-failure.json)、[此前已有账号结果](performance-warm.json)

检查门槛与性能门槛均通过。压测后负库存、漏预留、漏释放、重复退款、关闭未释放与跨商户孤立明细检查均为零。[库存与流水断言](stock-invariants.json)

此前通过 Windows `host.docker.internal` 转发的尝试出现同步超时，门槛失败，没有作为验收通过结果。改为 Compose 内直连后才通过；当前成绩不覆盖 Windows 宿主机转发路径、公网链路、最大容量、长期负载或资源独占环境。

## Router、FAQ 与真实模型分开测量

- **确定性 Router**：两名独立用户、约三十秒，首次精确菜名创建草稿，后续明确修改数量；20 次全部完成，成功请求 P95 708.64ms。未配置模型；与普通业务压力和构建任务同机重叠，不能与较空闲环境直接对比。初次测试错误地重复发送“首次创建”指令，已有草稿后转向未配置模型，18 次降级，门槛失败；修正场景为创建后修改并重新运行，未放宽检查。[结果](router.json)
- **FAQ**：39 条固定标注样本、11 类 FAQ、6 条无答案问题，每条 100 次。混合词法检索 Top-1 92.31%、Precision@1 96.77%、Recall@1 90.91%、无答案拒答 100%。这是固定集、本机内存检索结果，不是向量 RAG 或模型回答准确率。[结果及微基准](faq.json)
- **真实模型**：最终业务版本 `b81551f`，`deepseek-v4-flash`，三次只读推荐请求均 HTTP 200 / completed；延迟分别 4276.52、3633.50、4164.85ms，每次成功读取偏好与菜单，均发生两次模型调用。提供商累计报告输入 19,134 token、输出 1,475 token。只有三个样本，没有容量、全面质量或首 token 结论。[结果](real-model.json)
- **费用**：记录了提供商 usage；未读取账户账单、优惠/缓存计价或实时价格，金额未核实。保守预算不当作真实计费 token，未报告虚构人民币或美元成本。真实资金支付与退款仍未接入。

## 安全扫描与剩余限制

最终镜像使用 Trivy 0.75.0：网关扫描 OS 层，并扫描镜像内构建生成的 CycloneDX Maven SBOM；Agent 扫描 OS 和 Python 运行依赖。此前检出的可修复项已更新 Tomcat 11.0.26、Jackson 2.21.7 / 3.1.7、httpcore5 5.4.3，运行镜像去除不需要的 pip/ensurepip。[扫描摘要、镜像 ID 和剩余 CVE](security.json)

| 范围 | HIGH | CRITICAL | 有修复版本的 HIGH/CRITICAL |
|---|---:|---:|---:|
| 网关 OS | 0 | 0 | 0 |
| Java Maven SBOM | 0 | 0 | 0 |
| Agent OS + Python | 44 | 0 | 0 |

Agent 的 44 项 HIGH 包级发现涉及 8 个唯一 CVE，来自基础系统包，当前扫描库未提供修复版本。没有完成逐项可达性/可利用性分析；扫描政策通过不等于没有漏洞。当前建议作为本机演示交付，公开部署前审阅这些项并跟踪基础镜像修复。扫描范围没有包含数据库、Redis、Caddy、备份和 Prometheus 镜像，不能推及整套基础设施均无漏洞。

公网覆盖文件包含 Caddy HTTPS、Secure / SameSite Cookie、CSRF、HSTS、内部服务不暴露端口、关闭弱密码种子和启动防护。已校验配置语法；没有真实域名、证书签发与公网验证，不能称为公网上线。数据库应用账号仅限业务 schema，Flyway 仍需要 schema DDL 权限；多副本 Agent 的准入机制仍需改为分布式。

备份目前在同一主机，须另外复制到异机才能覆盖整机损坏；外部告警通知未配置。事件持久补读与有界实时队列已实现，未做长期 SSE 稳定性、磁盘满、主机断电或完整故障注入矩阵。付款、取消和超时的状态恢复依赖数据库事务与扫描任务，重启后数据可查询，不能据此声称任意灾难恢复零丢失。
